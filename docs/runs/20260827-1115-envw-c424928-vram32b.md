# Misura `20260827-1115-envw-c424928` — `granite4:32b-a9b-h` entra nella 3090?

> **Non è un run T0**: è una misura di capacità, eseguita durante la finestra di
> manutenzione esclusiva del 27/08 per falsificare l'assunzione su cui poggia la
> matrice EVAL di beta1 (`docs/piano_ricovero.md` §2.1 e §4.2) — «19 GB, quindi entra
> nei 24 GB della 3090». 19 GB è la dimensione del file, non l'occupazione a inferenza.

## Coordinate

| Campo | Valore |
|---|---|
| `RUN_ID` | `20260827-1115-envw-c424928-vram32b` |
| Ambiente | **ENV-W** — HP Z8 G4, RTX 3090 24 GB (24 576 MiB), 235 GiB RAM |
| **Esclusività host** | **`exclusive`** — finestra di manutenzione dichiarata dall'owner; `nvidia-smi` prima del run: **9 MiB usati, zero processi di calcolo**, nessun container vast.ai presente |
| Repo | `release/v0.0.2` @ `c424928` (irrilevante per la misura: dipende solo da Ollama e dal driver) |
| Runtime | Ollama in container con passthrough NVIDIA, driver 13.2, CUDA compute 8.6 |
| Modello | `granite4:32b-a9b-h`, id `2f8a7367d441`, **19 GB** su disco |
| Grezzi | `~/NORTHSTREAM-archive/20260827-1115-envw-c424928-vram32b/` |

## Risposta: **sì, entra — interamente in GPU, senza spill**

```
$ docker exec northstream-ollama ollama ps
NAME                  ID              SIZE     PROCESSOR    CONTEXT
granite4:32b-a9b-h    2f8a7367d441    20 GB    100% GPU     32768
```

| Grandezza | Valore misurato |
|---|---|
| **Picco VRAM osservato** | **19 788 MiB** su 24 576 (campionamento ogni 2 s) |
| **Margine residuo** | **4 788 MiB (~4,7 GiB)** |
| Ripartizione | **100% GPU**, 0% CPU — nessuno spill |
| Contesto allocato | **32 768 token** (default derivato da Ollama dalla VRAM disponibile: `total_vram="23.6 GiB"` → `default_num_ctx=32768`) |
| Latenza, primo caricamento | **101 s** (include il caricamento dei 19 GB da disco in VRAM) |
| Latenza, modello caldo | **3 s** (prompt breve) · **1 s** (prompt ~1 500 token) |

**Il dato che conta più del picco**: la VRAM resta a 19 730–19 788 MiB **indipendentemente
dalla lunghezza del prompt** (misurato con prompt breve e con prompt da ~1 500 token). La
KV cache dei 32k di contesto è **preallocata**, non cresce con l'uso: il picco osservato
è quindi il picco vero, non un limite inferiore da cui il consumo può salire durante una
sessione lunga. Per la matrice EVAL significa che il margine di 4,7 GiB è stabile e non
va eroso da prompt più lunghi, fino a 32k token.

## Le condizioni sotto cui la risposta resta valida

1. **Il modello deve essere solo.** 19,3 GiB su 24 lasciano 4,7 GiB: sufficienti per
   `granite-embedding:30m` (62 MB) accanto, non per un secondo modello di taglia media né
   per un tenant esterno. Conferma per misura la riga della tabella §2.1 del piano: «con
   un tenant sui 22 GiB **non parte**». Con la Z8 in noleggio vast.ai, la matrice EVAL su
   questo modello **non è eseguibile**: serve una finestra esclusiva, e va prenotata.
2. **Il contesto di default è 32k.** Se una combinazione della matrice EVAL richiedesse un
   contesto maggiore, la prealloca crescerebbe e il margine sparirebbe. Da verificare al
   momento in cui la matrice fissa i suoi parametri, non prima.
3. La misura è su **una** GPU da 24 GB con questa quantizzazione. Non dice nulla su
   modelli più grandi della matrice: quelli restano il caso d'uso di RP-0 / A100.

**Conseguenza per il piano**: l'assunzione regge, e **RP-0 non viene riaperto da questa
misura** — la riga «opzionale ma non archiviabile» di §4.2 resta valida per i modelli
oltre il 32b, non per il 32b stesso.

## Nota metodologica: la prima misura era falsa, ed è archiviata apposta

Il primo tentativo ha prodotto:

```
NAME                  ID              SIZE     PROCESSOR    CONTEXT
granite4:32b-a9b-h    2f8a7367d441    19 GB    100% CPU     4096
```

cioè apparentemente la risposta opposta — «non entra, Ollama va tutto su CPU» — con una
latenza plausibile (29 s) e una VRAM a 9 MiB. **Era un artefatto.** Il container Ollama
era stato ricreato poco prima con `docker compose up -d` **senza l'override GPU** che
`start-addon.sh --gpu` aggiunge, e girava senza passthrough:

```
$ docker inspect northstream-ollama --format '{{json .HostConfig.DeviceRequests}}'
null
$ docker logs northstream-ollama | grep 'inference compute'
msg="inference compute" id=cpu library=cpu ... total="235.8 GiB"
msg="vram-based default context" total_vram="0 B" default_num_ctx=4096
```

Contro la misura valida, dove la stessa riga dice:

```
msg="inference compute" id=0 library=CUDA compute=8.6 name=CUDA0
    description="NVIDIA GeForce RTX 3090" driver=13.2 type=discrete total="23.6 GiB"
msg="vram-based default context" total_vram="23.6 GiB" default_num_ctx=32768
```

Il log grezzo della misura falsa è archiviato come `inferenza-cpu-invalida.log` accanto a
quella valida: serve come esempio del modo in cui questa misura può mentire, perché
l'artefatto **confermava l'ipotesi attesa**. Un risultato che conferma ciò che si sospetta
è quello che si controlla meno.

**Controllo minimo da eseguire prima di ogni misura GPU su ENV-W**, da qui in avanti:

```
docker inspect northstream-ollama --format '{{json .HostConfig.DeviceRequests}}'   # non deve essere null
docker logs northstream-ollama | grep 'inference compute'                          # deve dire library=CUDA
```
