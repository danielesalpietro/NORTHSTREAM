## P-12 verificato secondo #46

`actions/checkout` è **verde in entrambi i run**, sullo stesso workspace del runner. È la
prova che serviva: prima del fix, la prima nightly su un workspace pulito funzionava e
**tutte le successive fallivano** con `EACCES … rmdir '.../trino/catalog'`, perché la
directory veniva creata `root:root` da Docker al primo `up`. Con `trino/catalog/.gitkeep`
nell'albero, la directory nasce dal checkout come utente del runner.

**Limite noto del fix, misurato**: `.gitkeep` risolve il *checkout pulito*, non
l'*aggiornamento di un clone esistente*. Su questo host, `git pull` in un clone che aveva
già la directory root-owned fallisce con
`error: unable to create file trino/catalog/.gitkeep: Permission denied`, lasciando
l'albero a metà. Stessa forma di P-11: un percorso di aggiornamento che la CI non può
vedere perché parte sempre da zero. Va nella stessa nota di migrazione di #45.

## T0.4 e T0.5 — perché non bloccano la release

Nessuno dei due è una regressione: `git diff` su `stream-agent/` dalla baseline è vuoto.
Sono entrambi test che interrogano l'agent, e la nightly li esegue dentro la finestra
cieca di **A-8/[#39](https://github.com/danielesalpietro/NORTHSTREAM/issues/39)**.

| Condizione | T0.4 | T0.5 |
|---|---|---|
| Nightly 08:59 (freddo) | PASS | FAIL |
| Nightly 11:48 (freddo) | **FAIL** | PASS |
| Nightly 12:01 (freddo) | **FAIL** | **FAIL** |
| **Riesecuzione a stack caldo, 2 giri** | **PASS ×2** | **PASS ×2** |

A freddo l'esito è una lotteria; a caldo è deterministico. La prova diretta è nel campo
che il test stesso legge:

```
nightly (T0.4 fallito):  buffered_events reported by /health: 0     ← a 85 s dall'avvio
riesecuzione a caldo:    {"status":"ok","buffered_events":38,...}   ← dopo 6 min
    giro 1:  T0.4 PASS (3s) · T0.5 PASS (32s)
    giro 2:  T0.4 PASS (0s) · T0.5 PASS (1s)
```

Che nei tre run a freddo siano falliti **tre insiemi diversi** di test (solo T0.5, solo
T0.4, entrambi) è il punto: non esiste "il test fragile" da irrobustire: esiste una
finestra cieca che si sposta e colpisce a caso fra i test che dipendono dall'agent.

**Conseguenza per il gate di release**: T0.4 e T0.5 possono essere considerati verdi, a
condizione di dichiarare *come* — «PASS a stack caldo» — finché il *warm-up gate* della
nightly non esiste. Senza quel gate, ogni nightly futura produrrà FAIL casuali e la
guardia di non-regressione resta indebolita.

## Verifica di P-11 (#45) — i tre stati del preflight

Il controllo aggiunto da #45 non è verificabile in CI per costruzione (ogni run parte da
volume inesistente). Verificato qui a mano, ricreando deliberatamente la condizione rotta.

| Stato del volume `kafka_data` | Esito del preflight | Exit |
|---|---|---|
| **assente** (installazione pulita) | `OK no pre-existing kafka_data volume — nothing to migrate` | 0 |
| **popolato dall'immagine vecchia** (dir `0:0` modo 775, file `1001:0`) | **`FAIL`** col messaggio completo (causa, sintomo, comando di rimedio) | **1** |
| **creato dall'immagine nuova** | `OK … is writable by uid 1000 (apache/kafka's user)` | 0 |

Tre stati, tre risposte distinte: il check **discrimina**, non fallisce a prescindere.
Nota metodologica: il controllo cerca il volume **per label**
(`com.docker.compose.project` + `com.docker.compose.volume`), non per nome — un volume
fasullo creato senza quelle label avrebbe prodotto un `OK` che non ha controllato nulla.
Il volume di prova è stato creato con le label corrette, ed è per questo che il ramo
`FAIL` si attiva davvero. Rimosso a fine verifica; stack riportato in stato sano.
