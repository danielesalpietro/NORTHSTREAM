## 2. Il fix

`stream-agent/app.py`: il contatore in RAM `_point_id` sparisce, l'id diventa una funzione
pura di `(topic, partition, offset)`:

```python
POINT_ID_NAMESPACE = uuid.UUID("ee4a4e8d-3dcb-5172-9f02-613e166fdef3")

def point_id(topic: str, partition: int, offset: int) -> str:
    return str(uuid.uuid5(POINT_ID_NAMESPACE, f"{topic}:{partition}:{offset}"))
```

Il namespace è **fissato come costante**, mai rigenerato: è derivato una volta come
`uuid5(NAMESPACE_URL, "https://github.com/danielesalpietro/NORTHSTREAM/stream_events")` e
scritto a mano nel modulo, così lo stesso record produce lo stesso id oggi e fra un anno.

**La trappola dell'handoff, misurata invece che creduta.** Tre processi Python con
`PYTHONHASHSEED` diverso, stessa chiave `northstream.public.orders:0:42`:

```
seed=1  uuid5=ec8d0209-51d9-5257-add5-749becddb89c   hash()=1091991438528393374
seed=2  uuid5=ec8d0209-51d9-5257-add5-749becddb89c   hash()=-8133865941778167228
seed=3  uuid5=ec8d0209-51d9-5257-add5-749becddb89c   hash()=-6472857424985534730
```

`hash()` cambia a ogni processo: avrebbe riprodotto A-3 con un travestimento migliore.
`uuid4()` non è stato preso in considerazione: perde l'idempotenza, che è metà del motivo
del fix.

## 4. L'assurdo, che è la notizia

La definition of done chiede: *«dopo un riavvio, nessun punto con id basso porta un evento
più recente di uno con id alto»*. **Applicata alla lettera, con la scelta (1) questa
condizione non può mai passare** — e non perché il difetto sia aperto, ma perché i punti
legacy conservano per sempre l'inversione che il difetto ha già prodotto. Oggi `id=1` porta
un evento delle 12:15:21Z e `id=32000` uno del 29/08: sono cicatrici, non ferite aperte.

Peggio: la condizione è **inesprimibile** sui punti nuovi. Gli UUID non hanno un ordine in
cui «basso» e «alto» significhino qualcosa, quindi un'inversione id/tempo non può nemmeno
essere formulata. Un criterio che diventa insensato proprio quando il fix funziona non può
essere il criterio.

La versione che misura la stessa cosa, e che ho eseguito: **nessun punto preesistente
cambia payload attraverso un riavvio.** È lo stesso guasto visto dal lato giusto — se il
punto che conteneva l'evento X ora contiene Y, è stato sovrascritto — e vale sia per i
legacy sia per i nuovi. Risultato, su tutta la collection e non su un campione:

```

id interi legacy: 32841 -> 32841   id UUID: 143 -> 153
punti preesistenti con payload CAMBIATO (sovrascritti): 0
punti preesistenti SPARITI: 0
punti nuovi: 10, di cui con id UUID: 10, con id intero: 0
```

## 5. T0.8: il commento prometteva più dell'asserzione

sulla crescita del conteggio, e il `reused` veniva osservato e mai asserito. **Non avrebbe

Ho allineato l'asserzione al contratto invece del contrario: il campione ora porta

`sample_ids` è diventato `sample_points`; i 200 punti del campione restano validi con id
UUID (verificato, non dato per scontato).

## 7. Limite residuo, dichiarato

L'id è unico finché **il topic non viene ricreato**: se Kafka perde il proprio volume o un
topic viene cancellato e rifatto, gli offset ripartono da zero e la stessa terna
`(topic, partition, offset)` indicherebbe un evento diverso — stesso id, sovrascrittura.
Non è teorico: è ciò che farebbe un teardown con `docker compose down -v`, già vietato per
P-10/#42. Vale la pena saperlo quando si deciderà la (2) in A-2.
